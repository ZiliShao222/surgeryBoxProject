# 手机端、硬件、摄像头与上位机架构方案

本文档整理最终产品形态下的系统架构：硬件全部集成到人体模型内部，摄像头独立放在外部，教师使用教师手机端，学生使用学生手机端，上位机负责低延迟接收摄像头画面和硬件速度并实时显示。

## 结论

推荐架构：

```text
[人体模型内部硬件]
  ESP32/ESP8266 + 编码器 + 舵机刹车 + 电机
        |
        | WiFi telemetry: position / speed / event
        v
[本地上位机 / Training Gateway] <--- USB / RTSP / WebRTC --- [外部摄像头]
        |
        | session records / status API
        v
[后端服务]
        |
        +--- [学生手机端]
        |
        +--- [教师手机端]
```

核心原则：

- 上位机保留，但定位改为“本地实时训练网关 / 显示主机”。
- 摄像头不经过硬件，也不经过云端再回传。
- 硬件无线发送速度、位置、事件到上位机。
- 上位机本地完成视频和速度叠加显示。
- 学生手机负责登录、训练交互、Quiz 和个人记录。
- 教师手机负责学生列表、训练记录、统计和历史趋势。
- 教师端第一版不需要实时视频监控，视频转发可作为后续可选功能。

## 系统角色

| 组件 | 位置 | 核心职责 |
| --- | --- | --- |
| 人体模型内部硬件 | 模型内部 | 编码器采集、速度计算、事件触发、刹车、电机回卷、无线遥测 |
| 外部摄像头 | 模型外部 | 拍摄训练区域或操作过程 |
| 本地上位机 / Gateway | 训练现场 | 接收摄像头和硬件数据，低延迟显示画面和速度，管理训练 session |
| 学生手机端 | 学生手上 | 登录、开始训练、答 Quiz、查看个人记录 |
| 教师手机端 | 教师手上 | 登录、查看学生列表、训练记录、统计结果 |
| 后端服务 | 本地服务器或云端 | 用户、角色、设备、训练记录、题库、统计 |

## 为什么仍然需要上位机

在本系统中，上位机不是传统意义上的“学生端”，而是低延迟实时融合节点。

系统有两条实时数据：

```text
摄像头视频流
硬件速度/位置遥测
```

这两条数据必须在一个本地节点汇合，然后叠加显示：

```text
视频画面 + position / speed / event overlay
```

这个节点就是上位机。

如果取消上位机，只能把这些实时任务放到学生手机、硬件板或云端：

| 替代方案 | 问题 |
| --- | --- |
| 学生手机承担上位机 | 外置摄像头接入复杂、手机性能差异大、权限复杂、发热和掉帧风险高 |
| ESP32/ESP8266 处理摄像头 | 不适合高质量低延迟视频处理和叠加显示 |
| 云端融合视频和速度 | 延迟高，依赖网络，不适合训练现场实时显示 |
| 教师手机承担实时显示 | 教师在场，无需承担主实时链路，且会增加复杂度 |

因此推荐保留上位机，并将其产品化为：

```text
Training Gateway
本地显示主机
训练实时融合盒
```

它可以是笔记本、mini PC、一体机、工控机或嵌入式主机。

## 上位机职责边界

上位机建议负责：

- 接收摄像头画面。
- 接收人体模型内部硬件的 WiFi telemetry。
- 本地低延迟显示训练画面。
- 在画面上叠加速度、位置、事件、阻力状态。
- 管理当前训练 session。
- 保存本地训练数据。
- 上传训练记录到后端。
- 必要时给学生端/教师端提供局域网 API 或 WebSocket 状态。

上位机不建议负责：

- 作为最终学生端移动 UI。
- 作为最终教师端移动 UI。
- 把实时视频主链路转发到云端再显示。
- 等待后端返回后再显示速度或事件。

## 摄像头接口选择

摄像头不必须是唯一指定接口，但第一版强烈推荐 USB UVC 摄像头直连上位机。

推荐优先级：

```text
USB UVC > HDMI + USB 采集卡 > 有线 RTSP/IP Camera > WiFi RTSP/WebRTC Camera > 手机摄像头
```

### 方案 1：USB UVC 摄像头

结构：

```text
外部摄像头 --USB--> 上位机
硬件 --WiFi--> 上位机
```

优点：

- 延迟最低。
- 稳定性最好。
- 不占用 WiFi 视频带宽。
- OpenCV / PySide6 读取简单。
- Windows 通常免驱或少驱动。
- 与硬件 WiFi 遥测互不干扰。

这是第一版最推荐方案。

### 方案 2：HDMI 摄像头 + USB 采集卡

结构：

```text
摄像头 HDMI 输出 -> USB 采集卡 -> 上位机
```

适合更高画质或更专业相机。

优点：

- 画质更好。
- 延迟可以较低。
- 上位机通常把采集卡识别为摄像头设备。

缺点：

- 成本更高。
- 多一个采集卡。
- 线材和供电更复杂。

### 方案 3：有线网络摄像头 / RTSP

结构：

```text
IP Camera --网线--> 路由器 --> 上位机
```

适合摄像头离上位机较远、可布网线、需要固定安装的场景。

优点：

- 摄像头布置距离更自由。
- 有线网络比 WiFi 摄像头稳定。
- 可使用 PoE 摄像头简化供电。

缺点：

- 延迟通常高于 USB。
- RTSP 缓冲需要优化。
- OpenCV 读取 RTSP 时要控制 buffer。

### 方案 4：无线网络摄像头

结构：

```text
WiFi Camera -> 路由器 -> 上位机
```

只有在无法布线时才建议考虑。

注意事项：

- 摄像头尽量走 5GHz WiFi。
- 硬件遥测走 2.4GHz WiFi。
- 使用专用路由器。
- 选择支持低延迟 RTSP 或 WebRTC 的摄像头。
- 避免消费级云摄像头，因为它们通常为了稳定会加大缓存，延迟较高。

### 方案 5：手机作为摄像头

可以用于原型验证，但不建议作为产品主方案。

问题：

- 手机固定不方便。
- 续航、发热、锁屏、权限、通知都会干扰。
- 如果同一台手机还要做学生端，会产生角色冲突。
- 不像可封装、可交付的训练设备。

## 硬件集成人体模型

硬件全部塞进人体模型内部是可行的，但需要注意工程设计。

推荐模型内部硬件：

```text
ESP32 或 ESP8266 控制板
编码器
舵机刹车
电机
电机驱动
稳压供电模块
急停按钮
维护 USB 口
WiFi 天线
设备二维码或设备编号
```

### 控制板建议

短期验证：

```text
继续使用当前 ESP8266 / Wemos D1
```

长期产品化：

```text
建议升级 ESP32，优先考虑可外接天线版本
```

ESP32 更适合产品化的原因：

- WiFi 稳定性和资源余量更好。
- WebSocket / MQTT / HTTP 更稳。
- 内存更大。
- OTA、日志、配置保存更方便。
- 可通过 BLE 做更好的手机配网体验。
- 可外接天线，适合藏在人体模型内部。

### 天线位置

不要把 ESP 天线深埋在电机、金属结构、电源线束附近。

建议：

```text
主控板可以在模型内部
天线尽量靠近非金属外壳
产品化优先使用外接天线
```

### 供电

建议分路供电：

```text
主控供电
舵机供电
电机供电
```

并确保：

```text
ESP GND
Servo GND
Motor Driver GND
Power Supply GND
全部共地
```

如果使用电池，需要额外考虑：

- 电池容量。
- BMS。
- 保险丝。
- 低电量保护。
- 充电口。
- 急停。

### 安全设计

建议加入：

- 物理急停按钮。
- 电机限位。
- 舵机动作限位。
- 过流保护。
- 看门狗。
- 断网策略。
- 训练中掉线提示。
- 回卷动作二次确认。

需要明确：

```text
断网时刹车释放还是锁定？
硬件掉线时上位机如何提示？
电机回卷是否必须人工确认？
```

## 网络拓扑

推荐使用专用双频路由器，不建议依赖校园网、医院网或公共 WiFi。

原因：

- ESP32/ESP8266 通常使用 2.4GHz。
- 公共 WiFi 可能开启客户端隔离，导致设备互相访问不到。
- 校园网可能需要网页认证或 802.1X，ESP 难以接入。
- 专用路由器能固定 IP、关闭 AP isolation、控制带宽和延迟。

推荐网络：

```text
专用双频路由器
├─ 2.4GHz：人体模型内部硬件
├─ 5GHz：上位机、教师手机、学生手机
└─ 可选：5GHz 或网线连接网络摄像头
```

如果条件允许：

```text
上位机 --网线--> 路由器
硬件 --2.4GHz WiFi--> 路由器
手机 --5GHz WiFi--> 路由器
```

这不违反“硬件和上位机无法有线连接”，因为有线连接的是上位机到路由器，不是上位机到硬件。

## 硬件遥测协议

硬件不应只发送事件，也应连续发送速度和位置。

建议遥测频率：

```text
20-50Hz
```

建议消息格式：

```json
{
  "device_id": "surgerybox-001",
  "session_id": "session-abc",
  "t_ms": 123456,
  "ticks": 2450,
  "position_cm": 12.42,
  "speed_cmps": 1.83,
  "event": null,
  "brake_state": "release",
  "sequence_index": 3
}
```

事件发生时：

```json
{
  "device_id": "surgerybox-001",
  "session_id": "session-abc",
  "t_ms": 124500,
  "position_cm": 14.02,
  "speed_cmps": 1.64,
  "event": "HighDamp",
  "brake_state": "locked"
}
```

### 第一版通信

可以继续使用 UDP 到上位机：

```text
硬件 -> 上位机：UDP telemetry
上位机 -> 硬件：UDP command
```

优点：

- 低延迟。
- 和当前代码接近。
- ESP8266/ESP32 都容易实现。
- 上位机作为网关可以屏蔽手机端不支持 UDP 的问题。

### 后续升级

后续可考虑：

```text
硬件 -> 上位机：WebSocket
硬件 -> MQTT Broker
硬件 -> 后端 API
```

但第一版建议先跑通：

```text
硬件 WiFi 遥测 -> 上位机实时 overlay
```

## 速度显示设计

推荐：

```text
速度计算：硬件端优先
速度显示：上位机本地实时叠加
速度记录：上位机/后端保存
```

硬件端最接近原始编码器数据，可以更稳定地计算：

```text
ticks
distance
dt
speed
```

上位机也可以做平滑显示，例如指数移动平均：

```text
display_speed = 0.7 * old_speed + 0.3 * new_speed
```

推荐频率：

| 数据 | 推荐频率 |
| --- | --- |
| 编码器采样 | 硬件中断，尽量高 |
| 速度计算 | 20-50Hz |
| 硬件遥测发送 | 20-50Hz |
| 上位机视频显示 | 30-60fps |
| 后端记录上传 | 1-5Hz 或事件触发 |
| 教师手机状态刷新 | 1-2Hz 或 WebSocket |

教师手机不需要接收 20-50Hz 原始数据。

## 上位机实时融合逻辑

上位机应将视频 loop 和 telemetry loop 分开。

基本逻辑：

```python
latest_telemetry = None

def on_telemetry(msg):
    latest_telemetry = msg

def on_camera_frame(frame):
    overlay = latest_telemetry
    draw_speed(frame, overlay.speed_cmps)
    draw_position(frame, overlay.position_cm)
    draw_event(frame, overlay.event)
    display(frame)
```

低延迟原则：

- 摄像头帧来了就显示。
- 遥测数据来了就更新缓存。
- 渲染时使用最新一条遥测。
- 视频不等待网络请求。
- 速度不等待后端返回。
- 后端不参与实时 overlay。

## 延迟目标

建议指标：

| 链路 | 目标延迟 |
| --- | --- |
| 硬件速度到上位机显示 | 50-100ms |
| USB 摄像头到上位机显示 | 50-150ms |
| 网络摄像头到上位机显示 | 100-300ms |
| 教师手机看到状态变化 | 300ms-2s |
| 训练记录保存 | 秒级可接受 |

必须区分：

```text
上位机实时显示 = 低延迟优先
教师手机 Dashboard = 准实时即可
后端训练记录 = 可靠性优先
```

## 手机端定位

### 学生手机端

学生手机端建议负责：

- 登录。
- 选择训练。
- 扫码绑定设备或 session。
- 开始训练确认。
- 答 Quiz。
- 查看个人训练记录。
- 必要时发送 OK / Continue 等响应。

学生手机端不建议负责：

- 外部摄像头主显示。
- 主实时视频 overlay。
- 直接处理硬件 UDP。

### 教师手机端

教师手机端建议负责：

- 登录。
- 查看学生列表。
- 查看当前训练状态。
- 查看训练结果。
- 查看统计图表。
- 查看历史趋势。
- 导出或分享报告。

教师端第一版不建议做实时视频监控，因为教师在现场。  
如后续需要视频预览，可以从上位机旁路转发低码率视频：

```text
上位机本地显示：1080p / 30fps / 低延迟
教师手机可选预览：480p 或 720p / 10-15fps / 可接受 0.5-2s 延迟
```

该功能不应影响上位机本地实时显示。

## 后端定位

后端负责：

- 用户认证。
- 学生/教师角色。
- 班级。
- 设备。
- 训练 session。
- 训练事件。
- Quiz 结果。
- 统计。
- 历史记录。

后端不负责：

- 实时摄像头主显示。
- 实时速度 overlay。
- 低延迟硬件控制主链路。

推荐策略：

```text
实时训练走本地
训练记录同步后端
教师/学生手机从后端读数据
```

## MVP 阶段规划

### Phase 1：本地低延迟闭环

目标：

```text
摄像头 USB 到上位机
硬件 WiFi 到上位机
上位机实时显示画面 + 速度
```

技术：

- 保留 ESP8266 或准备 ESP32。
- 继续使用 UDP 或 JSON UDP。
- 上位机接收 telemetry。
- 上位机在视频上 overlay speed / position / event。

### Phase 2：硬件改 Station 模式

目标：

```text
硬件不再开 surgeryBox 热点
硬件连接专用路由器
上位机和手机都在同一局域网
```

### Phase 3：手机学生端/教师端

目标：

```text
学生手机登录
教师手机登录
学生训练记录上传
教师查看学生记录和统计
```

第一版不要求教师手机看实时视频。

### Phase 4：升级 ESP32

目标：

```text
更稳定 WiFi
外接天线
更好 OTA
更好设备配网
更适合产品化
```

### Phase 5：可选视频转发

目标：

```text
教师手机可选查看低码率训练画面
```

该功能通过上位机旁路转发，不影响本地实时显示。

## 推荐最终部署形态

```text
人体模型
├─ 内部：ESP32、编码器、舵机、电机、电源、急停、维护口
├─ 隐蔽处：WiFi 天线、设备编号/二维码
└─ 外部：导管训练结构

外部摄像头
└─ USB UVC 摄像头，固定支架，对准操作区域

上位机 / Training Gateway
├─ 接 USB 摄像头
├─ 接专用路由器
├─ 接收硬件 WiFi telemetry
├─ 实时显示视频 + 速度 overlay
└─ 上传训练记录

专用路由器
├─ 2.4GHz：人体模型内部硬件
├─ 5GHz：上位机、教师手机、学生手机
└─ 关闭 AP isolation

手机
├─ 学生手机：学生端
└─ 教师手机：教师端
```

## 第一版推荐定案

第一版建议明确支持：

```text
摄像头：USB UVC 摄像头直连上位机
硬件：ESP8266/ESP32 通过 WiFi 向上位机发送 telemetry
上位机：本地实时显示画面 + 速度 overlay
学生端：手机登录、Quiz、记录
教师端：手机登录、学生记录、统计
后端：保存用户、训练记录和统计
```

第一版暂不做：

```text
教师端实时视频监控
云端视频回传
学生手机承担主摄像头显示
ESP32-CAM 作为主摄像头
硬件直接向手机发送 UDP
```

## 一句话总结

上位机在最终系统里仍然应该存在，因为它负责摄像头画面和硬件速度的低延迟本地融合显示。摄像头不必绑定唯一接口，但第一版最稳的是 USB UVC 摄像头直连上位机。教师端手机只看数据、记录和统计，不参与实时视频主链路；学生端手机负责登录、训练交互和 Quiz。硬件藏在人体模型内部，通过 WiFi 向上位机发送速度、位置和事件。
