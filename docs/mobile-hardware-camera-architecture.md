# 最终有线训练站、摄像头与软件端架构方案

本文档整理当前最终决策：人体模型内部硬件通过有线接口连接电脑上位机，外部摄像头也直接连接电脑上位机；学生在电脑上位机完成硬件训练，教师端和学生端仍以软件形式存在，但主要负责学习、练习、记录、统计和管理，不参与硬件训练的低延迟实时链路。

## 结论

推荐最终架构：

```text
[人体模型内部硬件]
  ESP8266/ESP32 + 编码器 + 舵机刹车 + 电机
        |
        | USB / Serial / 面板接口
        v
[电脑上位机 / 学生现场训练端] <--- USB / 工业相机接口 --- [外部摄像头]
        |
        | training record / quiz result / session summary
        v
[后端服务 / 本地数据库 / 云端数据库]
        |
        +--- [教师端软件]
        |
        +--- [学生端软件]
```

核心原则：

- 实时训练链路全部留在本地电脑上位机。
- 人体模型内部硬件不再以无线通信作为主链路，优先通过 USB/串口有线连接上位机。
- 外部摄像头直接连接上位机，优先 USB UVC 或工业相机接口。
- 上位机负责学生现场登录、硬件训练、摄像头画面、速度叠加、Quiz 和训练记录。
- 教师端软件负责学生记录、统计、历史趋势、错误分析和导出。
- 学生端软件负责学习材料、练习题、个人记录、课前预习和课后复盘。
- 后端只负责账号、题库、记录和统计，不参与硬件速度和摄像头画面的实时显示。
- WiFi/无线硬件通信降级为可选调试或备用方案，不作为第一版主实时链路。

## 系统角色

| 组件 | 位置 | 核心职责 |
| --- | --- | --- |
| 人体模型内部硬件 | 人体模型内部 | 编码器采集、速度计算、事件触发、舵机刹车、电机回卷、串口通信 |
| 外部摄像头 | 模型外部 | 拍摄训练区域和学生操作过程 |
| 电脑上位机 / 学生现场训练端 | 训练现场 | 学生登录、实时画面、速度叠加、硬件控制、Quiz、训练记录上传 |
| 教师端软件 | 教师设备 | 查看学生列表、训练记录、统计、趋势、导出报告 |
| 学生端软件 | 学生设备 | 学习材料、练习题、个人训练记录、非硬件训练内容 |
| 后端服务 | 本地或云端 | 用户、角色、题库、训练记录、统计和同步 |

## 为什么当前方案更稳

此前无线方案需要处理：

```text
WiFi 配网
设备 IP
UDP/WebSocket
局域网隔离
路由器稳定性
无线干扰
断线重连
手机端权限限制
```

现在硬件通过有线连接上位机后，实时链路变成：

```text
硬件 -> USB/串口 -> 上位机
摄像头 -> USB/工业相机接口 -> 上位机
```

优势：

- 延迟更低。
- 连接更稳定。
- 调试更简单。
- 不依赖现场 WiFi。
- 手机端不需要处理硬件实时通信。
- 上位机可以直接融合摄像头和速度数据。
- 现有 ESP8266/Wemos D1 和 PySide6 上位机代码更容易迁移。

## 上位机定位

上位机不再只是普通桌面模拟器，而是现场训练主机。

它负责：

- 学生登录。
- 选择硬件训练模式。
- 打开外部摄像头。
- 打开硬件串口。
- 向硬件发送 `Start`、`Stop`、`Winding`、`OK`、`Continue` 等命令。
- 接收硬件的 `POS`、`SPEED`、`Pain`、`HighDamp`、`LowDamp` 等消息。
- 将速度、位置、事件叠加到摄像头画面上。
- 在关键事件触发 Quiz。
- 保存本地训练记录。
- 训练结束后上传记录到后端。

上位机不建议负责：

- 教师端长期统计管理。
- 学生端课后学习和练习。
- 云端视频转发。
- 让后端参与实时画面显示。

## 人体模型内部硬件

模型内部保留：

```text
ESP8266/Wemos D1 或后续 ESP32
编码器
舵机刹车
电机
电机驱动
稳压供电模块
内部线束
```

模型外部建议露出：

```text
USB-C / USB-B / 航插数据接口
电源接口
急停按钮
电源开关
维护口
```

### 控制板选择

短期：

```text
继续使用当前 ESP8266 / Wemos D1
```

理由：

- 当前代码已经基于 ESP8266。
- 有线串口通信不再需要复杂 WiFi 能力。
- ESP8266 足够完成编码器、舵机、电机和串口遥测。

后续产品化可考虑：

```text
ESP32-S3 或 ESP32
```

升级理由：

- 更强性能。
- 更多资源。
- 更好的原生 USB 能力，尤其 ESP32-S3。
- 更好的长期维护空间。
- 后续如果恢复无线、OTA 或设备日志，余量更足。

但在当前有线方案下，升级 ESP32 不是第一优先级。

## 模型外壳接口设计

不要让一根线直接从洞里拉出来插到开发板上。建议做固定面板接口。

### 方案 A：USB-C 面板接口

推荐度最高。

```text
模型内部 MCU -> 内部短线 -> USB-C 面板母座 -> 外部 USB-C 线 -> 电脑
```

优点：

- 外观现代。
- 易插拔。
- 产品感好。
- 可同时走数据和低功耗供电。

注意：

- 必须使用支持数据的 USB-C 线。
- 面板接口要固定在外壳上。
- 内部线束要做应力释放。

### 方案 B：USB-B 方口

类似打印机接口。

优点：

- 稳定。
- 不容易松动。
- 比 micro USB 结实。
- 适合设备外壳。

### 方案 C：航空插头

适合更工业化和抗拉扯场景。

```text
模型接口：GX12 / GX16
外部线：航空插头转 USB/串口
```

优点：

- 牢固。
- 抗拉扯。
- 适合频繁插拔。

缺点：

- 需要定义线序。
- 需要转接到电脑 USB。
- 调试比 USB-C/USB-B 稍麻烦。

### 方案 D：直接线穿孔

仅适合临时原型，不建议最终产品使用。

## 线缆应力释放

模型内部必须做线缆固定，避免外部线被拉扯时损坏 MCU 或焊点。

建议结构：

```text
外部 USB 线
  -> 模型外壳面板接口
  -> 面板接口固定在外壳
  -> 内部短线连接 MCU
  -> 内部线束用扎带/线卡固定
  -> MCU 固定在支架或安装板上
```

不要：

```text
外部 USB 线直接穿孔插在 Wemos D1 的 micro USB 口上
```

这种方式容易松动、断线、拉坏开发板。

## 供电建议

电脑 USB 不应承担电机和舵机供电。

推荐：

```text
电脑 USB：负责 MCU 通信和少量控制板供电
外部电源：负责舵机、电机、电机驱动
所有 GND 共地
```

建议分路：

```text
MCU 5V / 3.3V
Servo 5V/6V
Motor supply
Motor driver supply
```

必须确保：

```text
MCU GND
Servo GND
Motor Driver GND
Power Supply GND
全部共地
```

如果为了简化产品外观，可以后续设计综合接口，但第一版建议数据和电源分开，方便调试。

## 安全设计

人体模型内部有电机和刹车结构，建议加入：

- 物理急停按钮。
- 电源开关。
- 电机限位。
- 舵机角度限制。
- 保险丝或过流保护。
- 串口断开保护。
- 上位机训练超时保护。
- 回卷动作二次确认。

串口断开时建议：

```text
motorStop()
进入安全状态
上位机提示硬件断开
当前 training session 标记为 interrupted
```

刹车断线时释放还是锁定，需要结合机械安全决定。第一版建议优先避免电机误动作。

## 硬件通信协议

### 第一版：沿用文本行协议

为了最快迁移，可以先把当前 UDP 文本协议搬到串口上。

上位机发送：

```text
Start
Stop
Winding
OK
OK1
Continue
OK2
Reset
```

硬件发送：

```text
SEQ:3,6.00,18.00,27.00,38.00
POS:12.34
SPEED:1.23
Pain
Pain2
HighDamp
LowDamp
Keep
ACK: Start
```

优点：

- 和当前固件/上位机思路一致。
- MCU 端改动小。
- Python 端容易接。
- 可以快速跑通。

### 第二版：升级 JSON Lines

产品化后建议使用每行一个 JSON：

硬件 telemetry：

```json
{"type":"telemetry","t_ms":123456,"ticks":2450,"position_cm":12.42,"speed_cmps":1.83,"event":null,"brake_state":"release"}
```

硬件 event：

```json
{"type":"event","t_ms":124500,"position_cm":14.02,"speed_cmps":1.64,"event":"HighDamp","brake_state":"locked"}
```

上位机 command：

```json
{"cmd":"Start"}
```

优点：

- 扩展字段方便。
- 日志可读。
- 训练记录更容易结构化保存。
- 后续与后端数据模型更一致。

建议节奏：

```text
先文本协议跑通
再 JSON Lines 产品化
```

## 串口参数

当前固件使用：

```cpp
Serial.begin(115200);
```

第一版建议保留：

```text
baudrate = 115200
```

如果后续遥测频率提高或 JSON 数据较长，可升级：

```text
230400
460800
921600
```

建议不要一开始就追最高波特率，先以稳定为主。

## 摄像头接口选择

当前方案中，摄像头也直接服务上位机。

推荐优先级：

```text
USB UVC 摄像头
USB3 工业相机
GigE/PoE 工业相机
HDMI + USB 采集卡
```

### 第一版开发验证

推荐普通 USB UVC 摄像头：

```text
1080p
30-60fps
手动对焦或固定焦距优先
USB 直连上位机
```

优点：

- 插上就能调。
- OpenCV 读取简单。
- 开发最快。
- 可以快速验证速度 overlay。

### 产品化版本

推荐工业相机：

```text
彩色
2MP-5MP
30-60fps
全局快门优先
USB3 或 GigE
C-Mount
支持 SDK
```

如果使用海康 MV-CU020-19GC 这类 GigE 相机：

```text
相机 --网线/PoE--> 上位机或 PoE 交换机
```

这适合摄像头距离电脑较远、想用网线固定安装的场景，但软件需要接入海康 MVS/GigE SDK。

## 上位机实时融合逻辑

上位机应分开处理摄像头和硬件串口。

```python
latest_telemetry = None

serial_thread.on_message = update_telemetry
camera_thread.on_frame = render_frame

def update_telemetry(msg):
    latest_telemetry = parse_hardware_message(msg)

def render_frame(frame):
    overlay = latest_telemetry
    draw_position(frame, overlay.position_cm)
    draw_speed(frame, overlay.speed_cmps)
    draw_event(frame, overlay.event)
    display(frame)
```

原则：

- 摄像头帧来了就显示。
- 串口消息来了就更新最新状态。
- 渲染时使用最新 telemetry。
- 不等待后端。
- 不让教师端/学生端软件进入实时显示链路。

## 延迟目标

| 链路 | 目标延迟 |
| --- | --- |
| 硬件速度到上位机显示 | 20-80ms |
| USB 摄像头到上位机显示 | 50-150ms |
| GigE 摄像头到上位机显示 | 80-250ms，取决于 buffer 和 SDK 设置 |
| 训练记录上传到后端 | 秒级可接受 |
| 教师端看到训练结果 | 秒级可接受 |

核心区分：

```text
上位机训练显示 = 低延迟优先
后端记录同步 = 可靠性优先
教师端/学生端软件 = 业务体验优先
```

## 教师端软件定位

教师端软件不直接连接硬件。

它负责：

- 教师登录。
- 学生列表。
- 训练记录。
- 班级统计。
- 单个学生趋势。
- 错题和事件表现。
- 导出报告。

教师端可以是：

```text
Web/PWA
桌面软件
移动 App
```

第一版不需要实时视频监控，因为教师在现场。

## 学生端软件定位

学生端软件也不直接连接硬件。

它负责：

- 学生登录。
- 学习材料。
- 练习题。
- 个人训练记录。
- 非硬件模拟训练。
- 课前预习和课后复盘。

硬件训练仍在电脑上位机完成。

## 后端定位

后端负责：

- 用户认证。
- 学生/教师角色。
- 班级。
- 题库。
- 训练 session。
- Quiz 结果。
- 训练事件。
- 统计。

后端不负责：

- 摄像头实时显示。
- 硬件速度实时 overlay。
- 电机/刹车低延迟控制。

训练结束后，上位机上传：

```json
{
  "student_id": "training01",
  "training_type": "remove_needle_simulator",
  "started_at": "...",
  "completed_at": "...",
  "elapsed_time": 25.4,
  "accuracy": 75.0,
  "max_pull_distance_cm": 20.0,
  "max_speed_cmps": 3.2,
  "events": [],
  "quiz_results": []
}
```

## 推荐实施步骤

### Phase 1：文档和代码框架

目标：

```text
明确有线训练站架构
上位机新增串口硬件连接框架
训练模块可选择 Serial/UDP connector
```

### Phase 2：固件串口协议

目标：

```text
硬件通过 USB 串口接收 Start/Stop/OK/Winding
硬件通过串口发送 POS/SPEED/Event
```

### Phase 3：上位机串口训练闭环

目标：

```text
学生在电脑上位机登录
摄像头显示
串口读取速度
画面叠加速度
事件触发 Quiz
训练记录保存
```

### Phase 4：模型接口产品化

目标：

```text
模型外壳固定 USB-C/USB-B/航插接口
内部线束固定
电源接口和急停按钮完善
```

### Phase 5：教师端/学生端业务软件

目标：

```text
教师端查看记录和统计
学生端查看学习材料、练习题和个人记录
后端同步训练数据
```

## 第一版推荐定案

第一版明确支持：

```text
硬件：人体模型内部 ESP8266/Wemos D1，经 USB/串口有线连接电脑上位机
摄像头：USB UVC 或工业相机，直接连接电脑上位机
上位机：学生现场训练端，负责实时显示、速度叠加、Quiz、记录上传
教师端：软件形式，查看记录和统计
学生端：软件形式，学习、练习和查看个人记录
后端：账号、题库、记录和统计
```

第一版暂不做：

```text
硬件 WiFi 作为主链路
教师端实时视频监控
学生手机直接连接硬件
云端参与实时画面 overlay
ESP32-CAM 作为主摄像头
```

## 一句话总结

最终方案采用“有线硬件 + 外置摄像头 + 电脑上位机低延迟训练 + 教师/学生软件端管理记录”的架构。人体模型内部硬件通过 USB/串口接入电脑上位机，摄像头也直接接入上位机；学生在电脑上位机完成硬件训练，教师端和学生端软件只负责学习、练习、记录和管理。这样实时链路最短、延迟最低、稳定性最好，也最适合当前代码逐步改造。
